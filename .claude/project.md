## 環境構成（DB / Clerk）

コード・docs から読み取れない運用情報。破壊的操作の可否判断に直結する。

| 環境 | DB | Clerk インスタンス |
|------|----|------------------|
| ローカル開発・テスト | ローカル/テスト用 Neon（**本番とは別**） | 開発インスタンス（`pk_test_` / `sk_test_`） |
| 本番 | 本番 Neon（**実在する**） | 本番インスタンス（`pk_live_` / `sk_live_`） |

- **本番の接続情報はローカルに存在せず、Vercel の環境変数にしかない。** これが本番への誤操作に対する最も強い防御である
- シードのテストユーザー（`bonjiri@example.com` 等）は**開発インスタンスにのみ存在する**。本番 Clerk には存在しないため本番にサインインできず、本番 DB にシードユーザー行が作られることはない
- Clerk の開発インスタンスとテストユーザーは **daily-hub / link-hub と共有している**。`SEED_PASSWORD` の変更は 3 リポジトリに波及するため、値の変更は揃えて行う
- `prisma/seed.ts` は `CLERK_SECRET_KEY` が `sk_test_` であることを要求する。本番インスタンスが `sk_live_` であるため、このガードは本番 Clerk への誤操作を確実に止める

## エージェントによる実機作業の注意

実機作業で判明した、コード・docs から読み取れない挙動。

### `prisma migrate reset` は Prisma がエージェント実行をブロックする

Prisma 7 は、Claude Code などの AI エージェントから `migrate reset` が呼ばれたことを検知して中断し、ユーザーの明示的な同意を求めるメッセージを出す。会話の中で事前に得た承認は同意とみなされない（メッセージがそう明記している）。PR #462 の検証で実際に通した手順:

1. コマンドを実行して、ブロックのメッセージが出ることを確認する（この時点では何も削除されない）
2. ユーザーに、実行するコマンド・目的・データが元に戻せない形で消えること・本番では実行してはならないこと・接続先が開発 DB だと判断した根拠を提示し、構造化された質問（AskUserQuestion）で明示的な同意を得る
3. 同意したメッセージの文面をそのまま（改行・引用符なしで）環境変数に設定して再実行する

```bash
PRISMA_USER_CONSENT_FOR_DANGEROUS_AI_ACTION='yes' npx prisma migrate reset --force
```

- 同意があいまいな場合は、「yes」などの明確な返答を改めて求める
- 無人実行（CI・スケジュール実行など）でユーザーに確認できない場合は中断する
- リセット後のシード投入手順は `docs/development.md` を参照

### `next dev` が `CLAUDE.md` に追記する

`next dev` は起動時に、`CLAUDE.md` へ Next.js のエージェント向けブロック（`<!-- BEGIN:nextjs-agent-rules -->` 〜 `<!-- END:nextjs-agent-rules -->`）を追記する。消しても、次に起動したときにまた追記される。

**このブロックはコミットしない。** `CLAUDE.md` は dev-commons が配布するファイルで、dev-commons の check-drift が毎週月曜 6:00 JST に各リポジトリの `develop` を正典と比較し、差分を検知すると Issue を自動で起票する。コミットすると、ドリフト Issue が毎週起票され続ける。

- コミット時はファイルを指定して `git add` する（`git add -A` / `git commit -a` を使わない）
- 作業ツリーから消すときは `git checkout CLAUDE.md`
